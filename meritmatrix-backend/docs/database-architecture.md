# Database Architecture

## Status

Milestone 3 (Schools & Academic Structure) is implemented and hardened.
This document covers the complete schema including authentication,
RBAC, school tenancy, and academic structures.

## Database engine

- **Engine**: PostgreSQL (required for staging/production)
- **ORM**: SQLAlchemy 2.x (declarative, typed)
- **Migrations**: Alembic, autogenerated from `Base.metadata`

A SQLite fallback exists solely so the automated test suite and local
`/health` smoke test can run without a running PostgreSQL instance
(e.g. in a minimal CI sandbox). It is explicitly rejected whenever
`ENVIRONMENT=production` (see `backend/app/database.py`).

## Conventions

- Primary keys: UUID (`uuid4`) unless there's a specific reason to deviate.
- Every table gets `created_at` / `updated_at` timestamp columns.
- Foreign keys are always indexed.
- Uniqueness and referential integrity are enforced at the database
  level (constraints), not just in application code.
- Historical/academic records are never hard-deleted; archival or
  soft-delete columns (e.g. `is_active`) are used instead.
- Enrollment history is append-only per academic year — changing a
  student's class does not overwrite prior enrollment rows.

## Entity Groups

### 1. Authentication & RBAC (Milestone 1 & 2)

| Table | Purpose |
|---|---|
| `users` | Platform identity (email, password hash, profile) |
| `roles` | Named collections of permissions (SUPER_ADMIN, SCHOOL_ADMIN, etc.) |
| `permissions` | Granular action permissions (schools.create, classes.read, etc.) |
| `user_roles` | Many-to-many: users ↔ roles |
| `role_permissions` | Many-to-many: roles ↔ permissions |
| `refresh_tokens` | JWT refresh token store |

### 2. Multi-Tenant School Tenancy (Milestone 3 Hardening)

| Table | Purpose |
|---|---|
| `schools` | Educational institution (name, code, address, etc.) |
| `school_settings` | Configurable preferences per school (1:1 with schools) |
| `user_schools` | **User-school membership** — associates users with schools |

The `user_schools` table is the key to multi-tenant isolation:

```
User ──┐
       ├── UserSchool ── School
Role ──┘

RBAC (User → Role → Permission) answers: "What can this user do?"
Membership (User → UserSchool → School) answers: "Which school(s) can this user access?"

Both checks are required for authorization.
```

- **SUPER_ADMIN** (has `system.admin` permission) bypasses school membership checks and can access all schools.
- **SCHOOL_ADMIN** must have an explicit `user_schools` entry to access a school. A SCHOOL_ADMIN for School A cannot access School B's data.

### 3. Academic Structure (Milestone 3)

| Table | Purpose |
|---|---|
| `academic_years` | School year period (e.g. 2025, 2026) — belongs to a school |
| `terms` | Term/semester within an academic year |
| `classes` | Class/grade group (e.g. Form 1A, Grade 7) — belongs to a school |
| `subjects` | Academic subject (e.g. Mathematics, English) — belongs to a school |
| `class_subjects` | Assignment of a subject to a class (both must be in same school) |

#### Key Constraints

- **Academic year**: `start_date < end_date` enforced at service layer. Unique `(school_id, name)`.
- **Term**: Must fall within its academic year's date range. Unique `(academic_year_id, term_number)`.
- **Class**: Unique `(school_id, code)` — same code allowed in different schools.
- **Subject**: Unique `(school_id, code)` — same code allowed in different schools.
- **Class-Subject**: Both class and subject must belong to the same school (cross-school assignment denied). Unique `(class_id, subject_id)`.

#### Current State

- Only one `academic_year` per school can have `is_current = True` at a time. Setting a new current year automatically unsets the previous one (service-layer logic).
- Only one `term` per academic year can have `is_current = True` at a time. Same automatic unsetting applies.

### 4. Cascade Delete Behavior

| Parent | Child | On Delete |
|---|---|---|
| School | SchoolSettings | CASCADE |
| School | AcademicYears | CASCADE |
| School | Classes | CASCADE |
| School | Subjects | CASCADE |
| School | UserSchools | CASCADE |
| AcademicYear | Terms | CASCADE |
| Class | ClassSubjects | CASCADE |
| Subject | ClassSubjects | CASCADE |
| User | UserSchools | CASCADE |

**Note**: Cascade delete is used for structural consistency. In production, schools and academic structures should be **deactivated** (via `is_active = False`) rather than deleted to preserve historical data integrity. Hard deletion of a school will cascade-delete all associated academic data.

## Security Model

### Authorization Flow

```
Request → Authenticated? → Has permission? → Member of target school? → Allowed
```

1. **Authentication**: Valid JWT token required.
2. **Permission check**: User must hold the required permission via their role. `system.admin` satisfies any permission check.
3. **School membership check**: For school-scoped resources, user must be a member of the target school (via `user_schools`). SUPER_ADMIN is exempt.

### IDOR Prevention

All school-scoped endpoints validate that the target resource belongs to a school the user is a member of. A SCHOOL_ADMIN for School A cannot access School B's resources by manipulating UUIDs in URLs.

### Cross-School Isolation

- Class-Subject assignments validate that both class and subject belong to the same school.
- All school-scoped queries filter by school membership.
- Database constraints enforce school-local uniqueness (e.g., class codes unique within a school, not globally).
